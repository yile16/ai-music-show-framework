# ADR 001：Agent 技术栈选型

**状态**：提案（Proposed） | **日期**：2026-05-20 | **决策者**：创作者

---

## 背景

框架模块 05 定义了 10 个 Agent（角色研究、精神提炼、歌曲方案、视觉设定、分镜、导演、审核、工具发现、数据结算、小说入口），需要在 Phase 3-5 阶段逐步实现。需要选定 Agent 开发的技术栈。

## 决策驱动力

1. 单人开发，时间有限 — 框架复杂度不能过高
2. 先用文档+模板跑通 2-3 期，再 Agent 化 — 不急于写代码
3. Agent 之间需要共享角色包、模板、产出物等上下文
4. 大部分 Agent 的工作模式是"读取结构化输入 → LLM 推理 → 输出结构化内容"

## 候选方案

### 方案 A：Mastra

- **是什么**：TypeScript 的 Agent 框架，`template-ai-storyboard-consistent-character` 项目使用
- **优势**：多 Agent 编排、Memory 管理、结构化输出、有现成参考项目
- **劣势**：TypeScript 生态、学习成本、项目相对新
- **适合**：需要多 Agent 协作 + Memory 管理的场景

### 方案 B：手写 Python + Anthropic SDK

- **是什么**：直接用 Anthropic SDK（或 langchain 的最小封装）写 Agent
- **优势**：最灵活、最轻、完全控制、与现有 `auto-novel-framework` 技术栈一致
- **劣势**：需要自己造 Memory 管理、Agent 通信、状态持久化
- **适合**：Agent 数量少、逻辑简单、追求最小依赖

### 方案 C：LangChain / LangGraph

- **是什么**：Python 生态最成熟的 Agent 框架
- **优势**：生态丰富、工具集成多、社区大
- **劣势**：抽象层次深、调试困难、"为了简单的事引入复杂的框架"
- **适合**：需要大量工具集成和多步骤链式调用的场景

### 方案 D：Claude Code + Skill 文件（当前即可用）

- **是什么**：不写代码，把每个 Agent 写成一个 `.md` Skill 文件，通过 Claude Code 调用
- **优势**：零开发成本、立即可用、模板即 Agent、适合文本阶段
- **劣势**：不适合需要实时/批量/自动触发的场景；人工仍需发起对话
- **适合**：Phase 1-2 的文本阶段，以及"需要人类在环"的 Agent

## 决策

**分阶段采用不同方案：**

| 阶段 | 方案 | 理由 |
|------|------|------|
| Phase 1-2（文本+素材） | **方案 D**：Claude Code + Skill 文件 | 零开发，立即可用。角色研究、精神提炼、歌曲方案等 Agent 直接写成 Skill 文件，通过对话调用 |
| Phase 3-4（复用+综艺） | **方案 B 为主 + 方案 D 为辅**：手写 Python + Anthropic SDK | 当流程稳定、需要批量跑时，把最稳定的 Agent（角色研究、视觉设定）写成 Python 脚本。不需要框架的复杂度 |
| Phase 5（规模化） | **方案 A 重新评估**：Mastra | 当 Agent 之间需要复杂协作（如分镜 Agent 需要调用视觉 Agent + 音乐 Agent + 审核 Agent）时，再评估是否需要 Mastra |

**当前结论：先用方案 D（Skill 文件），不进代码。Phase 1-2 验证后，再决定是否切换到方案 B。**

## 影响

- **正面**：避免过早架构化。Phase 0.5-2 期间专注内容验证而非代码开发。
- **负面**：方案 D 的 Skill 文件不能被外部系统调用，不适合批量或自动触发。
- **风险**：从方案 D 切换到方案 B 时有返工。但 Skill 文件本身就是 Agent 的逻辑描述，迁移成本可控。

## 替代方案被拒绝的原因

- **方案 A（Mastra）被延迟**：当前不需要多 Agent 协作，引入 Mastra 相当于在验证内容之前先验证 Agent 框架。等到需要时再评估。
- **方案 C（LangChain）被拒绝**：抽象层次深、调试困难、对于本项目的 Agent 场景过度设计。手写 SDK 调用 + prompt 模板足够。
